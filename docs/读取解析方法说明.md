# P5R 五维人物好感面板 · 读取与解析方法说明

本文说明面板**怎么拿到数据**：从哪个进程、哪块内存、哪个字节偏移读出来，遇到失效怎么自愈，
以及存档兜底路径用什么密钥和偏移解出来。所有内容对应 `P5ROverlay\Core\` 下的实际代码，
不是逆向笔记的二手转述，行号可直接对照。

- 适用游戏版本：**P5R PC 1.0.4**（Steam / Microsoft Store 同名进程 `P5R.exe`）
- 面板只做**只读**操作：`ReadProcessMemory` 读内存，`File.ReadAllBytes` 读存档，不写游戏内存、不改存档
- 语言 / 框架：C# / .NET 8 WinForms

---

## 0. 两条数据通路

```
                    ┌──────────────────────────────┐
                    │  WorkerLoop（后台线程，默认 5s）│
                    └──────────────┬───────────────┘
                                   │
              ┌────────────────────┴────────────────────┐
              │  游戏在跑？                               │
              └───────┬─────────────────────┬───────────┘
                     是                     否
                      │                      │
        ┌─────────────▼──────────┐  ┌────────▼─────────────────┐
        │ GameReader             │  │ SaveReader               │
        │ ① 找 P5R.exe            │  │ ① 找最新 DATA.DAT        │
        │ ② 取 exe 模块范围        │  │ ② 读文件头取 IV          │
        │ ③ 扫签名 → 五维地址      │  │ ③ AES-256-CBC 解密       │
        │ ④ 向前搜 Coop 数组       │  │ ④ 解第二段 zlib 得主数据  │
        │ ⑤ 每轮读 10 + 640 字节   │  │ ⑤ 按固定偏移取五维/Coop  │
        └─────────────┬──────────┘  └────────┬─────────────────┘
                      │                      │
                      └──────────┬───────────┘
                                 ▼
                        Snapshot{Live, Stats[5], Coops[]}
                                 ▼
                          界面刷新（Pages.cs）
```

内存路径给出的数值是**当前实时值**（存档前未写盘的变化也在内）；存档路径给出的是**最后一次保存时**的数值。
状态行会明确写「实时」还是「存档 07（11-18 16:52 保存）」，避免误读。

## 1. 附加进程（`GameReader.Attach`）

### 1.1 找进程

```csharp
Process.GetProcessesByName("P5R")
```

按进程名而非窗口标题，因为 P5R 在加载阶段还没有主窗口。找到第一个即用；一个都没找到时状态行显示
「等待游戏启动…」，不做重试计数（下一轮轮询自然会再找）。

### 1.2 打开句柄

```csharp
OpenProcess(PROCESS_VM_READ | PROCESS_QUERY_INFORMATION, false, pid)
```

只申请这两个权限，故意不要 `PROCESS_VM_WRITE` / `PROCESS_VM_OPERATION`：

- 从权限上保证面板**不可能**写坏游戏内存
- 部分反作弊/杀软会针对「申请写入权限」的行为告警，只要读权限不会有这个问题

失败（返回 `IntPtr.Zero`）最常见的原因是**权限不对等**：游戏以管理员启动、面板是普通权限，或者反过来。
状态行会直接提示「无法打开 P5R.exe，请以管理员身份运行面板」。

### 1.3 取模块范围

用 `CreateToolhelp32Snapshot(TH32CS_SNAPMODULE)` 枚举模块，找名字以 `P5R` 开头的那个，记下
`modBaseAddr` 与 `modBaseSize`。签名扫描只在 `[base, base+size)` 内进行——**不扫全进程地址空间**，
既快又不会误命中堆里的动态数据。

## 2. 五维：签名扫描

### 2.1 签名

```
4C 8D 35 ?? ?? ?? ?? 0F B7 FD
```

对应两条指令：

```asm
lea    r14, [rip + disp32]    ; 4C 8D 35 + 4 字节相对位移
movzx  edi, bpl               ; 0F B7 FD
```

`lea r14, [rip+disp32]` 就是「把某个全局数组的地址装进 r14」，`movzx edi, bpl` 是紧随其后的固定上下文。
两段合起来把「取五维数组地址」这个动作钉死，比单用 `4C 8D 35` 可靠得多。

### 2.2 遍历可读内存

`VirtualQueryEx` 按 region 遍历，只处理同时满足：

- `State == MEM_COMMIT`（已提交）
- `Protect` 不含 `PAGE_NOACCESS`（可访问）
- `Protect` 不含 `PAGE_GUARD`（不是守卫页，读守卫页会抛异常并破坏栈）

每个命中区域再按 **4 MB 分块** `ReadProcessMemory`，块内做朴素子串匹配。
分块的原因：exe 的 `.text` 段通常 10~30 MB，一次读会占用大块临时内存，也可能因跨不可读页而整体失败。

### 2.3 RIP 相对寻址换算

`lea` 指令长 7 字节，`disp32` 位于指令 `+3`，所以目标地址：

```
target = 指令地址 + 7 + disp32      // disp32 按 int32 有符号读
```

`disp32` 可能是负数（目标地址低于指令地址），所以必须按 `BitConverter.ToInt32` 有符号解释，
不能当 `uint`。

### 2.4 双重校验

命中不代表正确：`4C 8D 35` 这种三字节组合在代码里很常见。两个过滤器：

1. **形态校验**：`target > 0x10000`（排除空指针/低地址）
2. **数值校验**：从 `target` 读 10 字节，按 5 个 `short` 解释，要求每个都在 `[-1, 3000]`
   （`-1` 是游戏里「未初始化」的哨兵值）

1.0.4 实测命中 **2 处**：一处是真数组，另一处落在字符串表里，值是一堆大整数，被数值校验挡掉。

### 2.5 多命中择一

```csharp
foreach (var a in hits) {
    // 5 个值都合理，且至少有一个非 0 → 就是它
    if (sane && nz > 0) { best = a; break; }
}
```

要求「至少一个非 0」是因为字符串表那处可能恰好全落在合法区间；真正开局新档的五维也不会全 0
（知识至少为 0，但勇气/灵巧初始就有值）。若全部不满足，退回 `hits[0]`——宁可显示可能错误的数字，
也好过完全不显示。

### 2.6 五维结构

```
+0x00  short  [0]   知识   Knowledge
+0x02  short  [1]   魅力   Charm
+0x04  short  [2]   灵巧   Proficiency
+0x06  short  [3]   勇气   Guts
+0x08  short  [4]   体贴   Kindness
```

> **⚠ 这是全项目最容易出错的地方。**
>
> 数组顺序是 `[知识, 魅力, 灵巧, 勇气, 体贴]`，**和游戏菜单里显示的
> `知识 / 勇气 / 灵巧 / 体贴 / 魅力` 完全不同**。早期版本按菜单顺序硬套数组，
> 结果索引 1、4 互换，表现为「游戏里涨魅力，面板涨体贴」。
>
> 判定依据（不靠猜）：阈值表本身是对的，而**魅力 Lv2 只需 6 点**，是五项里最低的门槛；
> 这组「6 / 52 / 92 / 132」跟着索引 1 走，索引 1 被错命名成体贴，于是错位暴露出来。
> 修正后 `CoopTable.cs` 里 `StatNames` 与 `StatTh` 严格同序，并且注释写明了内存顺序。

> **渲染层单独解决排列问题**：数据按内存顺序读，界面却按游戏菜单顺序显示，
> 两者靠 `GameTables.StatDisplayOrder = { 0, 3, 2, 4, 1 }` 连接，含义是
> **「第 n 行显示哪一项」**（第 0 行显示下标 0 知识、第 1 行显示下标 3 勇气……）。
> 这个数组只作用于 `StatPage.OnPaint` 的循环顺序，`_stats` / `StatTh` / `StatLevel`
> 仍然用内存下标，所以错位不会重新出现。Python 版三份脚本用同样的 `ORDER` 表。

## 3. Coop：紧邻五维数组之前的定长数组

### 3.1 结构

内存里 Coop 是一段**定长记录数组**，位于五维数组之前，每条 **16 字节**：

```
+0x00  short  Confidant ID
+0x02  short  Rank（0–10）
+0x04  short  好感点数
+0x06  ...    10 字节补 0
```

运行时只放**已解锁**的角色，记录区末尾之后全是 0——这一点是定址算法的核心依据。

### 3.2 为什么不能写死偏移

实测 `五维地址 - Coop 起始 = 0x382`。但这个差值会随以下情况变化：

- 存档进度不同（已解锁角色数量不同，但数组是定长的，起始位置不变——差值主要受版本影响）
- 游戏小版本更新（1.0.1 / 1.0.2 / 1.0.4 的布局有细微差别）
- 某些改内存的 Mod

所以代码里**硬编码了 `0x382` 这个观测值但从不使用它**，只用来写注释。真正定址靠搜索。

### 3.3 搜索算法（`LocateCoop`）

```
窗口：  [五维地址 - 0x600, 五维地址)  共 0x600 = 1536 字节
起点：  窗口内每一个字节 p 都试一遍（1536 个候选）
步长：  16 字节
上限：  最多读 40 条
```

对每个候选起点 `p`，逐条验证：

| 条件 | 说明 |
|---|---|
| 终止 | `id == 0 && rank == 0 && pt == 0` → 记录区到此结束，正常收尾 |
| ID 合法 | `id` 必须在此前枚举的 24 个 Confidant ID 内 |
| 范围 | `0 ≤ rank ≤ 10`，`0 ≤ pt ≤ 3000` |
| 补零 | 每条 `+6 ~ +15` 共 10 字节必须全 0 |
| 条数 | 连续读通 `count ≥ 4` 才认，`count > bestCount` 才替换 |

「4 条」是下限而非精确值：开局只有摩尔加纳一个 Coop，但那时面板通常也没在用；
设 4 条是为了让随机数据几乎不可能凑出来（24 个合法 ID × rank 11 种 × 点数 3001 种 × 10 字节全 0，
连续 4 条偶然命中的概率可以忽略）。

### 3.4 ID 表

来源 Amicitia Wiki 的 `Confidant` 枚举。**P5R 新增角色是高位 ID**，接在 P5 的 1~21 之后：

| ID | 角色 | 塔罗 | | ID | 角色 | 塔罗 |
|---|---|---|---|---|---|---|
| 1 | 伊戈尔 | 愚者 | | 12 | 卡萝琳 & 贾斯汀 | 力量 |
| 2 | 摩尔加纳 | 魔术师 | | 13 | 岩井宗久 | 刑死者 |
| 3 | 新岛真 | 女教皇 | | 14 | 武见妙 | 死神 |
| 4 | 奥村春 | 女帝 | | 15 | 川上贞代 | 节制 |
| 5 | 喜多川祐介 | 皇帝 | | 16 | 大宅一子 | 恶魔 |
| 6 | 佐仓惣治郎 | 教皇 | | 17 | 织田信也 | 塔 |
| 7 | 高卷杏 | 恋爱 | | 18 | 东乡一二三 | 星 |
| 8 | 坂本龙司 | 战车 | | 19 | 三岛由辉 | 月 |
| 9 | 明智吾郎 | 正义 | | 20 | 吉田寅之助 | 太阳 |

### 3.5 失效自愈

`Poll()` 读 Coop 区失败（返回 `null`）时，说明游戏重启过、地址空间重新布局了，于是：

```csharp
_coopAddr = LocateCoop(_statsAddr);   // 就地重新定位，不打断面板
```

五维地址本身在游戏重启后一定失效（模块基址变了），这由 `Poll()` 返回 `null` → 外层
`Dispose()` → 下一轮 `Attach()` 处理。

## 4. 存档兜底解析（`SaveReader`）

游戏没开时，面板读**最新存档**，显示最后一次保存时的状态。

### 4.1 目录与选档

```
%APPDATA%\SEGA\P5R\Steam\<SteamID>\savedata\DATA01\DATA.DAT
                                          ...  DATA16\DATA.DAT
```

`Root` 属性先定位 `Steam` 下第一个含 `savedata` 的用户目录（不依赖 SteamID 具体值，换账号也不用改代码），
再对 01~16 逐个 `File.GetLastWriteTime` 取**最近修改**的那个。

注意：P5R 的存档编号和「游戏里看到的档位」不完全对应，多周目会有 `DATA11` 之后的备份目录，
所以用修改时间排序比用编号可靠。

### 4.2 文件头

| 偏移 | 长度 | 内容 |
|---|---|---|
| `0x00` | 4 | 魔数 `"DATA"` |
| `0x04` | 4 | CRC32 |
| `0x08` | 4 | 时间戳 |
| `0x0C` | 4 | flags（正常存档为 `0x80000000`） |
| `0x10` | 16 | AES-CBC 的 IV |
| `0x20` | ... | 密文 |

校验只检查前两个字节是不是 `D`、`A`（放宽到 4 字节 `"DATA"` 会因部分云同步中间态失败）。

### 4.3 解密

```
算法    AES-256
模式    CBC
填充    None        ← 关键，密文长度不是 16 的整数倍时按整块截断
密钥    base64: 3lOZS0kYSoOOtkC4c7IDfvNXnxIprUPTlUGVC3yBJF0=
IV      文件 0x10 起的 16 字节
输入    文件 0x20 起，长度向下取整到 16 的倍数
```

用 `PaddingMode.None` 而不是 `PKCS7`，原因：存档尾块可能被追加过 0（不同保存时机长度不同），
PKCS7 校验会失败；截断到整块后 AES-CBC 依然能正确还原前面所有块。

### 4.4 两段 zlib

解密后的明文从 `0x20` 开始**不是一个流，是两段 zlib 串联**：

| 段 | 解压后大小 | 内容 |
|---|---|---|
| 第 1 段 | 约 400 字节 | 存档预览信息（日期、地点、队伍），缩略图相关 |
| 第 2 段 | 198432 字节 | **主数据**，五维与 Coop 都在这里 |

代码不假设段的位置，而是从 `0x20` 起扫描 zlib 头 `78 9C / 78 DA / 78 01 / 78 5E`，
逐个头尝试 `ZLibStream` 解压，**解压结果 > 100000 字节的那一段**就是主数据。
这样即使某次更新给预览段加了字段、导致主数据段前移，也不需要改代码。

### 4.5 主数据里的固定偏移

| 数据 | 偏移 | 结构 |
|---|---|---|
| 五维 | `0x139E0` | `short[5]`，顺序同内存 |
| Coop | `0x136A0` | 26 条 × 16 字节 |

**存档里的 Coop 字段位置和内存里不一样**，这是第二个易错点：

```
内存：  +0x00 id   +0x02 rank  +0x04 点数
存档：  +0x06 id   +0x08 rank  +0x0A 点数     ← 前面多了 6 字节
```

所以 `SaveReader` 和 `GameReader` 的解析代码**不能复用**，必须各写一份偏移。

`COOP_N = 26`：存档是定长结构，26 条覆盖全部可能的 Coop（含未解锁，未解锁的 `id == 0` 直接跳过）。

### 4.6 为什么存档偏移可以写死

和内存不同，存档是**序列化后的定长结构**，字段位置由游戏的保存函数决定，与版本强相关但与进度无关。
只要版本对得上（1.0.4），偏移就是稳定的。这也是为什么代码里对存档用常量、对内存用搜索。

版本不符时的表现：`main.Length < 0x139E0 + 10` → 状态行提示「存档结构不符（版本不同？）」，
而不是显示一堆乱数。

## 4·5. 游戏内日期与时段（`GameReader.LocateDate`）

日历页要回答「今天是几月几日、白天还是夜晚」，这块数据不在五维/Coop 附近，是单独找出来的。

### 形状

8 字节一组，四个 `short`：

```text
51 00  04 01  51 00  05 00
└─┬─┘  └─┬─┘  └─┬─┘  └─┬─┘
 dayIdx  tag   dayIdx  时段
```

- `dayIdx`：从 **2016-04-01** 起算的天数，1-based 的「第几天」
  - 6/11 → 71，6/21 → 81，和 `(date - 2016-04-01).days` 完全吻合
  - 跨年不用特殊处理，`2016-04-01 + 273 天 = 2017-01-01`，一路加下去就是游戏学年
- 两个 `dayIdx` **一定相等**，这是整块结构最稳的特征（也是我们做校验的主条件）
- `tz`：时段。实测 **5 = 放学后 / 下午，6 = 夜晚**；0~4 是上午到白天，7 是深夜
- `tag`：`0x0100`~`0x0110` 之间，跟着日期/进度变，暂时只当校验用

### 怎么定位的（存档反推）

存档预览段（第一段 zlib，400 字节）里有**明文**的 `6月21日(二) 放学后 金城·宫殿`。
把 16 份 `DATA01`~`DATA16` 全部解开，靠这段明文就得到了一串**已知日期**：

```text
6/11 6/12 6/12 6/13 6/14 6/15 6/16 6/17 6/18 6/18 6/19 6/20 6/20 6/20 6/21 6/21
```

把它转成 `[63, 64, 64, 65, … 73]`，再拿这个序列去主数据（198432 字节）里逐字节比对。
直接比数值比不到（存的是 71 起算的另一套编号），于是换成比**「相邻两份存档是否相等」的掩码**：

```text
seq  = [63,64,64,65,…]         → same = [F,T,F,F,…]
主数据每个 offset 取 16 份同一位置 → 比 same 是否一致
```

只有 6 个偏移通过了这道筛，其中 `0x00A670` 的值是 `[71,72,72,73,…81]`，
和已知日期**严格相差常数 8**，且两个 `dayIdx` 相等 —— 锁定。

### 内存里的位置

和五维同属 `GlobalWork`，实测相对偏移 **-0x9190**：

```text
五维 0x1428653DC  →  日期 0x14285C24C      (0x1428653DC - 0x9190)
```

启动时先用这个偏移读一次，用 `IsDateBlock` 校验（两个 dayIdx 相等 + 范围 + tag）；
换了游戏版本偏移对不上，就退化成从五维往上搜 0x6000 字节找第一个合法块。
地址失效（游戏重启）会在下一轮 `Poll` 里重新定位，和 Coop 的处理一样。

### 存档里的位置

固定偏移 `0x00A670`，同样的 8 字节结构，读出来就是**存档那一刻**的游戏内时间。
游戏没开时日历页用它兜底，状态行会写「存档 DATAxx」。

### 换算

```csharp
DateTime d = new DateTime(2016, 4, 1).AddDays(dayIdx);
bool night = tz >= 6;
```

星期几直接 `d.DayOfWeek` 就行 —— 游戏用的是真实 2016/2017 日历
（存档预览写「6月21日(二)」，`2016-06-21` 确实是星期二）。

## 5. 轮询与状态机（`WorkerLoop`）

独立后台线程，与 UI 线程通过 `PostSnapshot` / `PostStatus` 交换数据（`BeginInvoke` 回到 UI 线程），
保证读内存不会卡界面。

```
while (!_stop) {
    未附加 → Attach()
    已附加 → Poll()  失败则 Dispose()，计数 +1
    snap == null → SaveReader.LoadNewest()
    有 snap → PostSnapshot()
    sleep = max(1, refreshSec) * 1000
    未附加时 sleep 上限压到 4s      ← 游戏没开时用 4s 探测，不必按用户的 10s
}
```

| 场景 | 行为 |
|---|---|
| 游戏启动中 | 每 4 秒试一次 `Attach`，状态行「等待游戏启动…」 |
| 已附加 | 每 `refreshSec`（默认 5s）读一帧 |
| 游戏退出 | `Poll` 返回 `null` → 断开 → 自动切到存档模式 |
| 手动刷新（F8） | `Thread.Interrupt()` 打断 `Sleep`，立刻进入下一轮 |
| 线程异常 | 写日志 + `Sleep(2000)` 重试，线程不退出 |

刷新间隔可设 1 / 2 / 5 / 10 秒。**不建议低于 2 秒**：单次轮询要读 10 字节 + 640 字节并做几次
`ReadProcessMemory`，频率过高没有收益，只是白白增加与游戏的调度竞争。

## 6. 从点数值到界面显示

### 6.1 等级判定

五维门槛是**累计点数**，不是「每级增量」。判定方式是取最后一个 `≤ 当前点数` 的门槛下标：

```
Lv = 满足 th[i] <= 当前值 的最大 i + 1
距下一级 = th[Lv] - 当前值        （Lv = 5 时显示「已满级」）
```

| 索引 | 属性 | Lv2 | Lv3 | Lv4 | Lv5 |
|---|---|---|---|---|---|
| [0] | 知识 | 34 | 82 | 126 | 192 |
| [1] | **魅力** | **6** | 52 | 92 | 132 |
| [2] | 灵巧 | 12 | 34 | 60 | 87 |
| [3] | 勇气 | 11 | 38 | 68 | 113 |
| [4] | 体贴 | 14 | 44 | 91 | 136 |

### 6.2 音符 ↔ 点数

游戏只显示 ♪，不显示内部点数，两套系统换算不同：

| 显示 | 五维 | Coop 好感 |
|---|---|---|
| ♪ | +2 | +5 |
| ♪♪ | +3 / +4 | +10 |
| ♪♪♪ | +5 / +7 / +10 | +15 |
| 加成 | 开运占卜 ×1.5（7→10 是单次上限） | 同塔罗面具 ×1.5；考试前十 ×1.2 / 第一 ×1.5 |

Coop 音符数封顶 3 个，即使带面具把 15 点抬到 22 点也只显示 ♪♪♪——**光看音符无法判断还差多少**，
这是面板直接显示内部点数的原因。面板五维页与好感页顶部各有一行换算提示。

### 6.3 Coop 好感需求

每级需求**按角色不同**，且不递增（例如东乡一二三 Lv9→10 只要 11 点，武见妙要 44 点）。
表转录自 bilibili 游戏 Wiki 各 COOP 页的「触发条件」栏，其中「星·东乡一二三」一行与
《P5R 官方完全攻略本》第 39 页完全一致。完整表格见 `Coop好感度需求表.md`。

升级瞬间好感点数**清零重算**，所以面板显示的是「本 Rank 内累计」，不是历史总和。

## 7. 已知限制

| 现象 | 原因 | 处理 |
|---|---|---|
| 「扫描不到五维签名」 | 游戏版本不是 1.0.4 | 换回 1.0.4，或按第 2 节自行找新签名 |
| 「无法打开 P5R.exe」 | 面板与游戏权限不一致 | 面板右键「以管理员身份运行」 |
| 五维对但 Coop 空 | 存档太早，解锁数 < 4 | 属正常，`count ≥ 4` 的下限所致 |
| 数值停住不动 | 游戏最小化/暂停，或已退出 | 面板会自动切存档模式 |
| 存档模式数值偏旧 | 存档模式读的是上次保存 | 属设计如此，看状态行的保存时间 |
| 全屏游戏看不到 | 悬浮窗在独占全屏下不显示 | 改窗口化 / 无边框窗口 |
| 五维和游戏里对不上 | 若为旧版本，可能是 2.6 节的顺序 bug | 更新到当前版本 |
